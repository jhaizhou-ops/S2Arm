# GAL Metal 渲染器设计约定（渲染线，10-18）

目标：实现 Ryujinx.Graphics.GAL 全部接口的原生 Metal 4 渲染器。Ryujinx Gpu 层（C#）→ C# 薄适配（sw/gfx/gal/cs）→ 本目录 C/ObjC 后端。
正确性参照 = Ryujinx 本体（Vulkan 后端）的语义：每个 GAL 方法照 ~/xbl/ref/ryujinx/src/Ryujinx.Graphics.Vulkan 的行为实现；
社区 Metal 后端（~/xbl/ref/ryujinx_metal_ref/src/Ryujinx.Graphics.Metal，MIT，半成品）只作「GAL 方法 ↔ Metal 映射」参照，不整份搬。

## 分层与调用
- C ABI 全在 gal_abi.h：导出函数直调（C# DllImport("nxgal")），参数 blittable，零封送。ABI 指纹由 tools/abi_hash.py 从 gal_abi.h 内容生成（C / C# 两端构建时各编一份，初始化比对），不手写版本号。
- 单线程：Gpu 层的 GPU 线程是唯一调用者（nxgal_current_sync 除外）。
- 句柄 uint32，0 = 空。枚举值 = GAL 枚举整数原样传，翻译在 C 端。

## 核心约定（gal_core.m / gal_internal.h）
- Metal 4：MTL4CommandQueue + 3 个命令分配器按栅栏轮换；一条 MTLSharedEvent 当栅栏。
- 编码器同一时刻至多一个；编码器之间全序屏障；拷贝编码器内相邻两条之间也加屏障（gal_blit_enc 负责）。
- 所有资源建好后 gal_res_add 进驻留集；释放走 gal_release_later（等在录 / 在飞命令用完）。
- 临时小块数据（常量、参数缓冲、上传暂存）用 gal_transient（按提交栅栏回收）。建块失败返回 NULL（已报红，附内存与低区空洞读数），调用方必须判空并跳过本次命令（10-20 丝之歌 iPhone 第 24 帧 clr_draw 写 NULL 崩）。
- 渲染通道按需开：gal_render_enc()；任何拷贝 / 计算 / 读回前 gal_blit_enc() 自动结束通道并落实挂起清屏。
- 两遍合一（缺省开，NXGAL_PASS_MERGE=0 关，gal_pass.m g_ph）：换目标组时深度模板附件不变（都有且同一张，或都没有）、新组颜色槽都是开遍时同槽同一张或空、通道尺寸不变 → 不收遍、只换逻辑组；逻辑组没有的颜色附件留在遍里当隐藏附件（管线里按物理格式、写掩码 0），本遍绘制要采样它先收遍。单测 tests/t_merge.m。
- 遍统计（NXGAL_PSTAT=1）可导出逐帧遍序列与断遍调用栈：NXGAL_PSTAT_DUMP=<文件>、NXGAL_PSTAT_DUMP_FRAMES=a-b；汇总行间隔 NXGAL_PSTAT_EVERY（缺省 300 帧）。
- 读回（GetData / GetBufferData）= gal_finish() 后从共享暂存读：这是「GPU 写回按需可见」的入口，Gpu 层的内存跟踪靠它把 GPU 写过的内容刷回客体内存。

## 资源绑定模型（第 4 / 5 / 6 块共同遵守）
- Capabilities：uniformBufferSetIndex 0、storageBufferSetIndex 1、textureSetIndex 2、imageSetIndex 3、extraSetBaseIndex 4、maximumExtraSets 4（共 8 集）。
- SPIR-V → MSL（SPIRV-Cross，argument buffers 第 2 档）：描述符集 s → 参数缓冲 [[buffer(s)]]，**每个阶段、每个集各一块**（离线库按单支着色器索引，一支的布局不能依赖同程序的其他阶段）。按 gal_prog.args 写：gal_arg.stages 每有一位就在该阶段该集缓冲的 offset 处写一次；缓冲 = GPU 地址，贴图 / 采样器 = MTLResourceID，数组连排；存储缓冲长度表（GAL_ARG_SIZES）写在参数缓冲里，入口多留的 [[buffer(24)]] 绑同一张表。采样贴图写采样视图 gal_tex.smp，图像写 gal_tex.tex。
- 参数表下标：0–7 描述符集；8–23 顶点缓冲（GAL_VB_BASE + 缓冲号）；24–29 后端内部（缓冲长度表等）。
- 着色器键：SPIR-V 内容哈希（SHA-256 前 8 字节）。Ryujinx 的特化在 Gpu 层完成（不同特化 = 不同 SPIR-V）。TargetApi.Vulkan 下 Ryujinx 磁盘缓存存的就是 SPIR-V、命中时直接 CreateProgram（不翻译），iOS 上即「客体代码 → 缓存 SPIR-V → 哈希 → 离线 metallib」，无运行时翻译。离线出库：tools/gal_offline.py。

## GAL 调用流录放对拍（渲染器主验收尺子，jhz 10-18 15:1x 定）
- 录：`new NxGal.Replay.GalRecorder(任意 IRenderer, 录像路径)` 包住交给 GpuContext 的渲染器（桩渲染器也行），边转发边写录像（sw/gfx/gal/replay/GalRec，GalRec.g.cs 由 gen_galrec.py 从 GAL 接口生成，录 / 放同一方法表，文件头带签名哈希）。
- 放 / 比：`build/gal/replay/galreplay diff <录像> [--out 目录] [--stride N] [--max-fails K]`：同一录像同步回放进参照渲染器（sw/gfx/gal/replay/RefVk：Ryujinx 1.3.2 Vulkan 后端 @ MoltenVK，源码未改）与 NxRenderer，每次绘制 / 清屏 / DrawTexture 后读回两边当前渲染目标比；输出首个分歧的调用序号、贴图格式 / 尺寸 / 不一致像素数 / 首处像素值、当前程序与渲染目标、之前 24 条调用，RGBA8 / BGRA8 目标另存两边 PNG。退出码 0 一致 / 1 分歧 / 2 录像错误。
- 判据：8 位 unorm / srgb / snorm 每字节差 ≤ 1；16 / 32 位浮点相对差 ≤ 1e-3（绝对 1e-5）；其余逐字节相等。
- 自测：`galreplay selftest <目录>`（脚本化调用录一段再对拍）。构建：make -C sw/gfx/gal && dotnet build sw/gfx/gal/replay/galreplay -c Release。
- 参照疑错（总指挥 10-18）：参照自身有错（MoltenVK 问题 / Vulkan→Metal 映射差，如 Mac 上 Ryujinx 塞尔达天空光束）。分歧先判参照是否合理，疑参照错的标「参照疑错」，带着色器键 + 状态 + 两边 PNG 交游戏线用原生 Vulkan 平台 Ryujinx 截图仲裁；确认参照错的登记进 replay/参照已知错误.tsv（按着色器键），galreplay 命中即记「参照已知错误」不计失败。不为贴合参照改成错的。

## 首遇现编（方案第九节，10-18）
- 建程序（CreateProgram）离线库 / 持久缓存都没命中 → 后台线程（QOS_CLASS_USER_INITIATED，低于渲染 / 游戏线程的 UI 档；iOS 2 路并发；10-28 起缺省，原 UTILITY 被宿主负载饿住、渲染线程首用等它时优先级反转，见坑记录）异步 SPIR-V→MSL→Metal，程序状态 Incomplete；
  GPU 线程第一次取用（gal_prog_get / 阻塞 CheckProgramLink）时没编完就等——口径同参照 Ryujinx Vulkan 后端（ShaderCollection.IsLinked 阻塞），从不跳过、从不画错。
- 持久缓存 NXGAL_SHADER_CACHE_DIR=<目录>：<键>.msl + <键>.rec（口径版本校验），下次跳过 SPIRV-Cross；Metal 系统缓存再省掉编译。
- 开关：NXGAL_ASYNC_XC=0 同步；NXGAL_XC_LOG=<文件> 每支耗时；nxgal_prog_xc_stats 计数。SPIRV-Cross 用本仓 sw/third_party/spirv_cross，iOS 静态库 make ios。
- Mac 读数（动森进岛段录像 234 支）：SPIRV-Cross 平均约 3 ms / 支、Metal 约 12 ms / 支；持久缓存命中后合计 28 ms。真机分布待量。

## GPU 缺页的来源（10-19 帧率能耗线查，方案 5b-3 / 研究 Metal越界.md ⑤-1）
- 研究已证：Air 与 iPhone 上 12 类着色器访存都是软缺页（读回 0、写丢弃），造不出缺页。
- 旧库 ~/.s2arm/run 下全部出过 kIOGPUCommandBufferCallbackErrorPageFault 的局（7 个 host.log）：缺页**从来不是本进程第一个 GPU 错误**——
  之前 5 例是被别的进程的错误连坐丢弃（InnocentVictim），2 例是本进程挂死（Hang），其中 5 例缺页前已「重建队列照常跑」。
- 本机系统日志 3 天内仅有的 WindowServer 缺页（10-19 15:52:58.227）：前 1.2 秒内 WindowServer 自己先被连坐丢弃 8 次，落在旧库四局连坐重建的同一窗口。
- 结论：缺页是「命令被丢弃后照常往下跑」的次生现象（被丢的上传 / 拷贝没执行，之后的绘制用到没写好的数据），不是另一类着色器访存。
  现行处置已断这条链：命令缓冲任一出错即判红、写现场、_exit(86)（gal_core.m，485eb71 起）；起因的挂死由着色器越界钳位 + 循环上限（gal_spvx.m）防。
- 射程：只看了本机旧库局目录与本机系统日志；mini / Air / 两台测试机的系统日志没查。被丢命令里具体是哪一步（索引取数 / 顶点取数等不归软缺页管的硬件单元）没有定位——出错即退出后不再可达。

## 8a-1 游戏数据缓冲零拷贝（10-19 摸底，未动手）
- 现状：渲染器已有零拷贝入口 nxgal_buf_create_host（newBufferWithBytesNoCopy，16 KB 对齐外扩；> 4 MB 分窗按取址懒建；进驻留集前过驻留安全阀）。
  但上游 Ryujinx 的 GPU 缓冲（Gpu/Memory/Buffer.cs）一律 CreateBuffer(size) + 同步时从客体内存拷贝（SetData），只有线性贴图回写缓冲（TextureGroup.cs:661）
  走 GetHostPointer + CreateBuffer(nint)；渲染器的 nxgal_prepare_host_mapping 目前恒返回 0（连这条也不放行）。
- 要做的事（Ryujinx 补丁 + 渲染器）：Buffer 建时若 GetHostPointer 拿得到单段宿主地址，就包装客体内存（不建副本）；同步 / 回写对这类缓冲是空操作
  （CPU 写与 GPU 写都直接落在同一份内存，Switch 本来就是共用内存）；仍需写跟踪的只剩贴图、着色器、池等「有副本」的对象。
- 头号风险：驻留集会把整段缓冲钉成 wired、不计进程 footprint——旧库 10-18 内核恐慌根因。全部游戏缓冲改零拷贝，等于把这个风险放到所有缓冲上。
  前提：先量清 iOS 上驻留集钉 wired 的确切行为（按页还是整段、释放时机），按 GPU 实际取址分窗；驻留安全阀按整机 wired 上限把关并报红。
- 第二风险：GPU 写与 CPU 读同时落同一份内存，Ryujinx 原有的「回写前等 GPU」次序没有了，要逐处核（信号量 / 报告值本来就直写，无影响）。
- 验法：GAL 录像录的是复制模型（建缓冲 + 写数据），回放验不到零拷贝；要游戏局（Mac 动森先），读 frames.tsv 的 upload_n / rb_us 与整机 wired 峰值。
  M0 动森 Mac 能出帧之后做。

## 着色器全量预编进包（10-19 总指挥令，帧率能耗线）
- 出包：`graphics/tools/shader_pack.sh <产物根> <输出目录>`，不启动游戏。抽取（shbake/nxsh_extract.py）→ Ryujinx 原翻译器出每个程序的 SPIR-V（shbake/ShaderBake.cs，旧库 a7276a3 搬入）→ gal_xc 出离线索引 → 用索引记录拼宿主程序二进制（nxgal_prog_binary 同格式）写 Ryujinx 磁盘缓存 → gal_offline.py 编 metallib。产物 gal.metallib / gal.idx / shcache/<程序号>/ 整个进包 Documents/资源包/shaders/。
- 运行时（graphics/loop/ShaderPack.cs）：渲染器初始化后开离线库、把 shcache 克隆进 Ryujinx 缓存目录（按包指纹：shader_pack.key + shcache 文件名 / 长度 / .toc 全文；指纹不符、目录不是包种的、缺或截短包里的文件 → 整份换成包内的并报红），再由 Ryujinx 读缓存：程序按二进制建，不重翻、不现编。
- 翻译口径两件补丁（ryujinx 0035 / 0036）：翻译器记下读过哪些特化状态，缓存匹配只比读过的；顶点按「片元读全部通用输入」翻（阶段独立），顶点结果不随配对的片元变。
- 能力表按出包目标固定（iPhone：BC / ASTC / ETC2 / 16 位紧凑、共享内存 32 KB），不按出包这台 Mac 查（ShaderBake.TargetDeviceCaps）。
- 计数：frames.tsv shader_miss = 离线库未命中 + 运行时 Metal 现编（gal 持久缓存只存 MSL，命中也要现编，照样计）；xlate_n = Ryujinx 当场翻的程序数（包没覆盖到的）。
- 前提：GraphicsConfig.EnableShaderCache 必须在 RegisterProcess 之前置 true（缺省 false = Ryujinx 磁盘缓存整个关；10-19 前 S2Arm 一直是关的，暖局不降的根因之一）。

## 程序配对来源：为什么动森配得出、暗黑2 / 巫师3 / 暗黑3 配不出（10-20 帧率能耗线查，总指挥要求写清）
- **配对**：把顶点 vs 和片元 ps 配成一个程序。Ryujinx 磁盘缓存按程序存，基础管线也按程序编。只有单阶段函数（阶段单独翻译进 gal.metallib）时，Metal 函数已经在库里，但运行时 Ryujinx 仍要现翻 Maxwell，管线仍要现建。
- **动森配得出**：着色器装在 NintendoWare 着色器档案里，档案自带程序表（程序 / 变体号 → 各阶段），shbake 规则直接读这张表（ShaderBake.cs 第 3 步「`#` 变体组」），配出 16032 个、去重后 9326 个程序。这是游戏数据本身给的配对，不是参照局；但只有用这种容器的游戏才有，不通用。
- **其他三款配不出**：抽取工具能拿到单阶段着色器，却没有程序表。暗黑2 是 CASC 里每个阶段一个 .bin（6903 支），巫师3 是 shadernx.cache（29584 支），暗黑3 1324 支。结果是程序只剩计算着色器（暗黑2 26 个、巫师3 46 个、暗黑3 0 个）。另有一条 BAHS / 偏移头「vs 紧跟 ps」规则，这三款都没命中。
- **通用方案（静态配对，创新方案一第二落点，10-20 批）**，按通用程度从高到低：
  1. **不依赖配对的部分先做成零配对**：阶段独立翻译（0037）之后，顶点按「片元读全部 32 个通用输入」翻，翻译结果与配对无关。Ryujinx 缓存改为按阶段存宿主代码、运行时按阶段组合成程序，这样任意组合都是 xlate 0。动森同样适用，而且能去掉 9326 个程序里不同组合重复存放的同一阶段。
  2. **管线**：接口固定（32 个通用输出全写）后，任意 vs 和任意 ps 都能链接。10-20 已量（psobench/pairbench.m，M5 Max，动森 60 支）：交叉组合 60 个全部建成；两个阶段都编过的新组合建基础管线中位 25.9 ms，顶点编过、片元首次 35.6 ms。Metal 没有可用的按阶段复用，每个新组合都要付整份编译。所以首遇零延迟只能靠离线把组合配出来，按阶段存只省 Ryujinx 翻译，省不掉管线。「两阶段都首次」那组中位 10.8 ms 偏低，是本机以前出包编过、命中了系统着色器缓存，不作数。
  3. **配对来源**（不依赖参照局）：游戏数据里的程序表（动森类容器，按容器格式各写一个读取器，可复用到同引擎的其他游戏）；引擎命名规则（暗黑2 文件名 vs_x / ps_x 同主干、巫师3 缓存条目同技术号）；游戏可执行文件里创建程序的调用（静态推导，创新方案一）。三者都只在出包时运行，产出程序表，进同一条 shbake 流程。
- **暗黑2 实测（10-20）**：
  - **SHAD 容器**：着色器 .bin 是暴雪 SHAD 容器，文本表 + 排列宏表（nxsh_extract.shad_table），162 个包全部能解析，排列数 = 代码记录数；抽取时把来源记成 `@shad<排列号>|宏=值,…`。
  - **同主干规则只覆盖一半**：同主干内「共有宏取值一致」即配对，会配出 23860 个程序（第一个宏为最低位），按旧局缓存真值（--ref-cover，6 份，84 个图形程序）只覆盖 43 / 84；另一种进位顺序配出 31008 个，只覆盖 23 / 84。
  - **漏掉的三类**：
    - 通用全屏顶点 × 只有 ps 的后处理主干（tonemap / fxaa / bloom 等）；
    - 跨主干组合（vs_models × ps_alpha_threshold）；
    - 同主干但共有宏取值不同（atmosphere_apply 的 HEIGHT_FOG_MODE），说明还有一张 SHMD / PRM[ 排列表没读。
  - **从主程序推配对（graphics/tools/shbake/exe_pairs.py，出包时抽到 SHAD 包自动跑）**：
    - 做法：每个着色器文件 <阶段>_<名>.bin 在主程序里有名字串 <名>；构造程序的代码会紧挨着引用一个 vs 名和一个 ps 名（如 models_v 0x125dbbc / alpha_threshold_p 0x125dbdc）。
    - 规则：窗口 W 字节内的 vs 引用 + ps 引用 = 一对；配对内宏取值按「共有宏一致」展开。
    - 读数：覆盖旧局缓存真值（34 份、去重 85 个图形程序）85 / 85。
    - 窗口扫描：

      | 窗口 | 对数 | 覆盖 | 程序数 |
      |---|---|---|---|
      | 32 | 67 | 81 / 85 | 25211 |
      | 64 | 72 | 85 / 85 | 25351 |
      | 128 | 83 | 85 / 85 | 26643 |
      | 256 | 98 | 85 / 85 | 27927 |
      | 1024 | 133 | 85 / 85 | 291422 |

      窗口太小会漏（32 漏 4 个），太大假配对暴涨；64～256 稳定，取 128。
  - **窗口规则会失效的情形**（经验规则，靠真值覆盖率兜底）：
    - 编译器把两次引用排得很远（内联 / 指令调度），会漏，表现为覆盖率下降；
    - 名字放在数据表里、经指针间接引用（本工具只扫 ADRP + ADD，不扫 8 字节指针重定位；暗黑2 这批名字的数据指针引用 0 处），会漏；
    - 运行时拼名（格式串 + 变体），名字串在主程序里不存在，会漏；
    - 一个函数里连续建多个程序（vs1 ps1 vs2 ps2 挨着），会多出交叉的假配对，只多编、不影响正确性。
  - **反例**：121 个着色器名里有 31 个在主程序里连主干都不存在（assao 一组、skybox、velocity / overdraw / quad_efficiency 等调试与 PC 版内容）。它们不会按名字加载，不配是对的；这个结论待更深场景的真值确认。
  - **结论**：材质数据（hd 下 json / model 等）里没有主干名或宏名；主干名、宏名字符串在主程序里，组合是引擎代码按材质属性拼出来的。所以暗黑2 的配对来源是可执行文件（创新方案一），不是数据表。上面这条全组合规则不满足「只编实际引用的组合」，没有合入。
- **判据**：每款纯静态冷局（不带参照包）shader_miss 0、xlate_n 0、pso_n 0。动森作为回归款，接口改成按阶段存之后，读数不能退。

## RE 引擎程序表（怪猎崛起，10-21 画面着色器线 pair）
- **根因**：怪猎包 5473 个程序全是计算、图形 0 个。RE 引擎着色器装在 SDF 文件（魔数 `SDF\0`，pak 里 620 个路径）里，旧抽取只按「控制段 + 机器码相邻」逐支认、没读文件自带的程序表，顶点 / 片元只能阶段单独翻译，运行时每个图形程序 Ryujinx 现翻（Mac 带存档局当场翻译 54，读档后黑屏等现编 >60 秒）。
- **SDF 程序表**（nxsh_extract.scan_sdf）：头 = 魔数 + u16 版本 + u16 记录数 + u64 字符串区终点；+0x10 起每条记录 0x108 字节：+0 名字偏移、+8 输入布局表、+0x10 起 6 个 u64 = vs / hs / ds / gs / ps / cs 着色器块偏移；块 = [控制段长][机器码长][控制段][机器码]。一条记录 = 引擎能建的一个程序，来源记 `<文件>#sdf|<记录名>`、变体号 = 记录号，走 shbake 的「# 变体组」规则。
- **补丁链**（re_pak.py）：KPKA 4.0 条目表，`re_chunk_000.pak` 后按补丁号升序读 `.patch_NNN.pak`，同一路径哈希后读的盖先读的；只抽最新版。旧做法整包盲扫 zstd 帧，3.2 万条被换掉的旧版也抽：唯一键 66283 → 26210，抽取 123 s → 14 s。
- **读数**（只出配对统计，--ref-cover 两局真值）：规则程序唯一键 49608、按客体代码去重 32990，真值覆盖 0/54 → 54/54。
- **收窄试过、被证伪**：材质文件 MDF 记着母材质路径与标志（位 0 双面、位 1 透明测试）；母材质路径 + 版本号 2011060894 的路径哈希 = SDF 条目。按标志只留材质会选的 X / AX / TSX / ATSX 组合，配对统计 32990 → 25506、54/54 不降；但收窄包的 Mac 带存档局里，标志全 0 的 NPC_Skin 等母材质照样用了 ADepthWrite / AZPrePass 等 A 变体（4 个程序现翻）——A 变体由运行时效果选，材质标志不是它的来源。不收窄。真值 54 个是读档黑屏前的前缀，不能拿它证明哪类渲染路径用不到。
- **透明测试变体**：nvn_uses 认出 RE 引擎取函数指针的写法（函数开头定表基址），判出怪猎从不调 nvnColorStateSetAlphaTest，不出「开」变体（八方2 UE4 经 GOT 读的写法同样认出）。
- **管线归档体积**（收窄包实测：60046 个渲染管线 2.07 GB，平均约 34 KB / 个）：按 pass 类别（全表、有片元、按阶段键去重 38381 个）：Clip 变体 33%、Forward 11%、Deferred 10%、系统 / 后处理 / 界面 10%、Shadow 10%、DirectDeferred 8%、Vfx 7%、DepthWrite 5%、其它 4%、Debug 2%、Pick 1%。

## 管线预建（着色器全量预编第 2 步，10-20）
- 依据（动森 Mac 冷局）：现建 165 个管线 2.58 s；用到的 136 个程序里 113 个各 1 个管线，多管线的差在顶点布局（14）与片元输出（9）。两者出包都不可知。
- 2a 两级建：基础管线 = 片元输出（颜色格式 / 混合 / 写掩码）留空，首遇按本次状态特化（psobench：特化中位 0.00 ms、均 0.03 ms；完整建 34 ms、留空基础 26 ms）。入口见 gal_be.h「管线特化」。
- 2b 顶点自取（gal_vpull.m，NXGAL_VPULL=1）：顶点着色器按取数表自己读顶点缓冲并解码，管线键去掉顶点布局。代价：基础管线编译 26 → 39 ms（出包承担）；运行时 GPU 代价待测试机1 A/B。
- 2c 出包预编（shader_pack.sh ④）：每个「顶点自取 + 带片元 + 不写层号」的图形程序一个基础管线、每个计算程序一个计算管线，生成 Metal 4 管线脚本（shbake/pso_gen.py，与运行时 pso_desc(…, unspec=1) 逐字段相同：8 个颜色附件全留空、拓扑未指定），applegpu-nt 按 GPU 架构离线编成 gal_pso.<架构>.<分片>.bin（平均每片约 300 个：一次喂 1.1 万个内存涨到 50 GB 以上；10-21 起分片边界按内容定——按函数名排序、按名字哈希切，增删一个程序只动 1–2 片，见 pso_gen.py 头注释；本机与 mini 从同一队列领片并行编，见 shbake/pso_dist.sh）。不用 metal-tt：它把整个 gal.metallib 打进归档（170 MB / 架构）。运行时按本机 MTLDevice.architecture 开全部分片，建基础管线时依次查，命中即特化。
- 命中不了的（顶点没自取、只光栅化、写层号、多重采样 / a2c 等基础键里的非缺省值）照旧首遇现建，frames.tsv pso_n 计数。
- Metal 3（iOS 18–25，待 M1 后落地）：没有特化接口，也没有 MTL4 管线脚本格式。退路 = 顶点自取后管线键只剩「程序 × 片元输出」，Metal 3 的 MTLBinaryArchive 只能按完整描述命中，片元输出出包不可知 → 首遇现建、计数报红（不跳过绘制）。覆盖率在 Metal 3 路径落地时用同一局实测。
- **归档与系统版本（10-20）**：
  - **绑定关系**：管线归档里是 GPU 机器码，绑定系统自带的 GPU 编译器。测试机2（iOS 27.0）载入用 26.5 SDK、platform_version ios 26.0 编的归档，73 片全部报「not compatible with current OS」，退成首遇现建（那局 208 个）。
  - **函数库不受影响**：gal.metallib 是 AIR 中间码，跨系统大版本向后兼容，同一局 iOS 27 上 shader_miss 0、xlate 0。只有归档要按版本出。
  - **出包**：每个系统大版本出一份 gal_pso.<架构>.<ios|macos><大版本>.<分片>.bin，用 SDK 大版本相同的 Xcode 的工具链编（/Applications/Xcode*.app 自动找；本机 Xcode 26.6 → iOS 26，Xcode-27 + Metal 工具链 27.1 → iOS 27）。运行时按本机架构 + 大版本选。成本：管线段按版本数倍增（动森约 105 s → 210 s）。
  - **玩家升级到包里没有的大版本**（例如包只有 26 / 27，系统升到 28），退路如下：
    1. **察觉**：载入时没有本版本归档，或载入失败，都报红进日志，并标记「需重建」。
    2. **重建**：包里同时带管线描述脚本（pso.*.mtl4-json，与出包同一份；只是 JSON，动森约 30 MB，zstd 后很小）。首启时后台线程按描述逐个建基础管线（MTL4Compiler + PipelineDataSetSerializer 收二进制），建完序列化到 Documents/S2A/pso/gal_pso.<架构>.<平台><大版本>.bin，下次启动直接载入。
    3. **重建期间不卡游戏**：启动器在进游戏前显示「正在为新系统准备着色器 x / N」，按出包时的程序顺序（同一容器先、计算着色器先）建。玩家可以跳过；跳过后后台继续建，游戏里首遇的管线由渲染线程现建（每个 26～38 ms，照计 pso_n），后台建好的立即可用（同一个编译器对象，后到的直接命中）。
    4. **代价估计（待真机量）**：动森约 1.1 万个基础管线 × 约 30 ms ÷ 后台并行 4 路 ≈ 80 秒。暗黑2 等大配对的款，要先靠宏取值推导把组合降下来，否则重建时长和包体都超线。
    5. **判据**：iPhone 上删掉本版本归档、起冷局，第二次启动 pso_n 为 0；重建期间游戏内 >100 ms 帧计数照报。

**为什么补配对规则没用（代码核过）**：
- 几何：渲染器报 `supportsGeometryShader: false`，Ryujinx 把「顶点 + 几何」转成计算着色器执行。转计算的程序 Ryujinx 自己既不写也不读磁盘缓存；shbake 遇到也主动跳过（ShaderBake.cs PhaseA 的 `ShouldConvertVertexToCompute` → `skip_vtg_compute`）。所以即使配成程序也进不了包，运行时首遇照样现翻。**影响：首局卡顿**（马车8 Mac 局现翻 1 支即此）。
- 曲面：渲染器不认 hs / ds 阶段，程序建不出来，相应内容不画。**影响：画面完整**（暗黑2 地形等）。

**三件事与工作量估计（AI 时间，未校准；顺序见 曲面几何设计.md 第四节）**：
1. **转计算程序的磁盘缓存**（Ryujinx 补丁）：ShaderCache 写入转计算程序；ParallelDiskCacheLoader 不再丢弃；GALP 宿主二进制给计算段加阶段标记；缓存版本 +1。约 200 行，含验证 60–90 分钟。
2. **shbake 几何配对 + 离线转换**：含 gs 的程序按规则或冷局记录配对，离线跑同一个 VertexToCompute / GeometryToCompute，SPIR-V 进 gal.metallib 与缓存；known_gap 的 gs_unpaired、vtg_compute 归零。约 150 行，60 分钟，依赖第 1 件。
3. **曲面支持**（渲染器新功能）：gal_xc / gal_prog 的三种入口、gal_state 管线描述、gal_draw 两步绘制（计算写因子 + drawPatches），加 t_draw 单测。2–3 小时，另加暗黑2 / 巫师3 与 Vulkan 参照的录放对拍。
**判据**：各款 known_gap 三项为 0；冷局 shader_miss 0、xlate 0；曲面 / 几何程序录放对拍逐像素一致。

## 坑：脚本里「$变量紧跟全角字符」（10-20 帧率能耗线）
bash（3.2 与 5.x 都是）在 UTF-8 区域下把紧跟的全角字符读进变量名，`set -u` 直接退出。10-20 shader_pack.sh 的 `$NU，` 让合入后自动出包 acnh / botw 着色器阶段全红约 40 分钟，开发机缺省区域下跑不出来（门禁照绿）。规矩：变量后面接非 ASCII 一律写 `${变量}`；graphics/ 下 .sh 已全改（扫 `\$[A-Za-z_][A-Za-z0-9_]*(?=[^\x00-\x7f])` 为 0）；仓库 tests/shell_lint_test.sh 只扫 tools / pack / tests，已请测试出包线扩到全仓。

## 诊断：真机按线程 CPU（S2A_THR_CPU=<秒>，gal_thrcpu.m，缺省关）
每 <秒> 往 stderr 打「[线程CPU]」全部线程占一核百分比 + 线程名 + 线程号，不截断。Mac 真宿主与外部量具（proc_pidinfo）同窗口差 ≤0.5%。真机诊断局：`tools/sched.sh submit acnh --env=S2A_THR_CPU=30 …`。

## 坑：非录制线程读回占主栅栏号 → 延后释放早放（10-21 帧率能耗线）
- 现场：暗黑2 Mac 局第 110 帧主队列回执 kIOGPUCommandBufferCallbackErrorInvalidResource（命令缓冲引用失效资源），出错缓冲栅栏 223；同一刻宽屏包装层刚「重新放宽」（旧贴图拷进新贴图后 Release），紧接着内存跟踪在客体线程上回写（读回）。
- 根因：主栅栏号 g_gfence + 1 是在录命令缓冲的身份（gal_release_later、gal_cb_id 的已用区间 / 写栅栏登记都按它记）。多线程后端里客体线程的读回走一次性命令缓冲，旧代码也从 g_gfence 取号：
  渲染线程录到一半时被它占掉 G + 1，在录命令缓冲提交时变成 G + 2；录制期间挂在 G + 1 上的延后释放随读回完成就被放掉、移出驻留集，在录命令缓冲里还引用着它。
