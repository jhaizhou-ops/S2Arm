# 快速测试与单款精修流程

写给想尽快验证一个改动、或想把一款游戏从「起不来」修到「能玩」的贡献者。这里写的是维护方每天实际在用的做法：工具都在仓库里，读数都有出处（10-26 普查 151 款、九款精修的记录）。环境、出包、起局开关的完整参考见 [贡献者开发测试套件](贡献者开发测试套件.md)，本文不重复。

结论先说：

- **能不起局就不起局。** 读代码、读日志、反汇编、单测、离线重算能回答的问题，不要拿游戏局去答。
- **普查一款游戏用一条命令**：`bash tools/quicktest/one_game.sh <源包文件夹>`，典型 4–5 分钟，会给出「通过 / 失败 + 第一个失败点」。
- **单款精修的循环是：快测定位第一失败点 → 用诊断开关或真值对拍找根因 → 写单测（旧代码红、新代码绿）→ 修 → 同一产物根一局确认。** 每一圈都应该是分钟级，不是小时级。
- **自检只在提 PR 前跑一次**（`bash tools/contrib_check.sh`）；它只跑你改动波及的步骤。真机、能耗和第二层验证交给维护方的合入列车。

## 1. 时间预算

| 环节 | 典型耗时 | 维护方实测 | 超了说明什么 |
|---|---|---|---|
| 读代码 / 日志 / 单测回答问题 | 秒到分钟 | — | — |
| 解包（`pack/stages/unpack.sh`） | 1–2 分钟 | 136 款中位 93 秒 | 源包异常大或要解 nsz / xcz |
| 精简档出包（`--lite --target mac`） | 半分钟 | 130 款中位 24 秒 | 改写遇到新形态、要现改写的模块很大 |
| Mac 零配置局 | ≤ 2 分钟 | 124 局中位 102 秒，上限 121 秒 | — |
| **快测一款合计** | **4–5 分钟** | **通过的 71 款中位 257 秒** | — |
| 完整出包（iPhone，含着色器全量预编） | 大作 1 小时以上 | 斯普拉遁3 在 MacBook Air 上着色器段超过 75 分钟 | 只在要出给玩家的包、或要量首遇 / 能耗时才出 |
| 任何一局游戏 | ≤ 300 秒 | 硬上限 | 要更长先在 issue 里说明 |

规矩：**改代码之后要验证，先找最便宜的一档。** 精简档不编着色器全量，Mac 局首遇时现编兜底，所以它不能拿来量首遇卡顿、帧率或能耗。要量这三样才用完整出包。

## 2. 普查式快测：`tools/quicktest/one_game.sh`

```sh
bash tools/quicktest/one_game.sh <源包文件夹 | 解包目录> [<输出目录>]      # 输出目录缺省 build/quicktest；给解包目录就跳过解包
```

它做四件事：解包 → 精简档出包 → Mac 局（经维护方 `entry_check.sh`（`$S2A_PRIVATE_TOOLS`）起：自动玩家开，有存档 / 进局路线就用；精简档走通用，`QT_DUAL=1` 时直连优先、没出成直连库退到通用；缺省 100 秒，到可操作场景后接着玩到局时长；崩了用同一产物根自动补一局）→ 定性。`结果.tsv` 末列「进局」= 自动玩家到 MARK（游戏场景里可操作）：是 / 疑似 / 否。结束时打一行摘要，往 `<输出目录>/结果.tsv` 追加一行；日志精简留在 `<输出目录>/logs/<名>/`（各阶段红黄行、`host.log` 前 2 MB、自动玩家的 `ap_mark.png` / `ap_end.png`）。工作目录缺省跑完就删，`QT_KEEP=1` 保留：保留的产物根 `work/<名>/roots/*@现行` 可以直接拿来反复起局，不用再出包（见 3.1）。

常用环境变量：

| 变量 | 作用 |
|---|---|
| `QT_RUN_S` | 局秒数，缺省 100 |
| `QT_KEYS` | 你自己的 `prod.keys`，缺省 `~/.switch/prod.keys` |
| `QT_KEEP=1` | 保留产物根，接着做单款精修 |
| `QT_FULL=1` | 不用精简档（要量首遇 / 宽屏时用，慢得多） |
| `QT_DUAL=1` | 同时出直连库，Mac 局直连优先（只在通用模式已通过的款上用） |
| `QT_NAME` | 工作 / 日志目录名（缺省取源文件夹名） |
| `QT_UNPACK_ONLY=1` | 只解包，留下解包目录（普查本机解包、远端出包跑局用） |

**第一失败点**按这个顺序判：崩溃 → 游戏 Break → 首帧 → 直连退回。都没有就是「通过」。判法在 `tools/quicktest/verdict.py`，可以离线对任何局目录重算（`python3 tools/quicktest/verdict.py <局目录>`）。

| 第一失败点 | 含义 | 下一步 |
|---|---|---|
| `解包` | 我方解包工具没解开 | 这算我方缺陷，不算游戏不支持。先换一份完整原件确认不是源文件坏，再报 issue 附 `unpack.out` |
| `出包：改写` / `出包：着色器` … | 出包某个阶段停了 | 看 `logs/<名>/refresh.log.red` |
| `稳定崩溃：客体代码（main+0x…）` | 两局都在游戏代码同一处崩 | 3.2 的 `S2A_DIAG_DUMP` 读崩点前的寄存器和内存 |
| `稳定崩溃：abort` / `C#未处理异常` / `NET GC 堆` | 崩在我方宿主或服务层 | 看 `host.log` 里 `CRASH 信号` 之后的栈 |
| `偶发崩溃` | 两局只崩一局 | 不能靠「再跑一局没崩」排除，见第 5 节第 6 条 |
| `游戏Break：原因 … 位于 …` | 游戏自己判定出错后主动退出 | 多半是某个系统服务的回答不对，用 3.3 的 IPC 对拍 |
| `首帧` | 局里没出图 | 看【红】行和线程现场（`S2A_STALL_DUMP_S`），先分清是在等服务还是在等 GPU |
| `直连异常` | 直连局打了「【红】直连异常（不切换，继续跑）」（10-26 起运行中不再退回通用） | 看 host.log 里这行写的原因 |

「通过」只说明零配置能起来、出了首帧、局里没崩。能不能玩到可操作场景，要看有没有 `ap_mark.png`，以及这张截图里是不是真的进了游戏（第 5 节第 9 条）。

## 3. 单款精修

### 3.1 循环

1. `QT_KEEP=1` 快测一次，拿到第一失败点和产物根。
2. 之后只改代码、不重出包，用同一个产物根反复起局：
   ```sh
   S2A_CS=1 S2A_IN=<输出目录>/work/<名>/roots/<款>@现行 bash runtime/run_mac.sh <款> <局目录> 100
   python3 tools/quicktest/verdict.py <局目录>
   ```
   `run_mac.sh` 会自己 `make host`，只编你改到的部分。只有改了出包阶段（改写器、着色器翻译、系统数据）时，才需要重新出包。
3. 用 3.2 / 3.3 的工具找到根因，**先写单测，让旧代码红、新代码绿**，再改。
4. 同一产物根跑一局确认越过原失败点，再快测一次，看下一个失败点。

### 3.2 诊断开关（只在 Mac 宿主生效，缺省关）

| 开关 | 用途 | 出处 |
|---|---|---|
| `S2A_DIAG_DUMP=<模块>+0x<偏移>[:x<寄存器>[+0x<加数>]:<字节>][,…]` | 执行到游戏的某条指令时打出全部寄存器，可选再打出某个寄存器指向的内存；读不了的地址不会崩。用来看某个调用的入参、某张表的内容 | `runtime/src/diag_brk.c` |
| `S2A_DIAG_STAMP=<点1>,<点2>,…` | 按线程给几条指令打时间戳，量两点之间的空窗（区分被切走和真在执行） | 同上 |
| `S2A_DIAG_DELAY=<点>:<毫秒>[:<次数>]` | 执行到时人为睡一会，把竞态窗口拉长，偶发崩溃变成稳定复现 | 同上 |
| `S2A_IPC_RECORD=<文件>` | 记录每一次系统服务请求（服务、命令号、入参、返回码、出参）；Ryujinx 真值用同一份记录代码 | `compat/tree/src/Ryujinx.Common/S2ARecord.cs` |
| `S2A_STALL_DUMP_S=<秒>` | 出图停住多久就打一次全部线程现场（缺省 10） | `runtime/src/ap_host.c` |
| `S2A_ALLOC_TRACE=1` | 每次 GC 之间各项的分配拆账 | `services/aot/Compose.cs` |
| `DM_NVN_GPUPROF=<首帧>[-<末帧>]` | 直连模式下逐个编码器的 GPU 时间 | `graphics/nvn/gfx/nvn/nvn_mtl.m` |
| `S2A_DIRECT_REC=<起始帧>:<帧数>` | 直连模式逐帧存 PNG（会降帧率，量帧率和能耗的局别开） | `graphics/nvn/host_adapt.m` |
| `S2A_AP_LIVE=<文件>` | 实时通道：局里往文件追加一行。`REC:<名>` 录下一次出图（要同时开 `S2A_FRAME_REC=<目录>`，见 `graphics/nvn/docs/frame_replay.md`）；`PASS:<名>` 实局下一帧打逐笔日志（`host.log` 的 `[pass]` 行）并截图存 `<帧录目录或局目录>/<名>.png`（录像回放不了的款用它）；别的行记「不认」 | `tests/autoplay/autoplay.c` |

崩点给的偏移（例如 `main+0x37c6c8`）配合游戏模块的反汇编看。地址是模块内偏移，与加载基址无关。

### 3.3 拿 Ryujinx 当真值对拍

我们的系统服务层就是 Ryujinx，因此「同一款在 Ryujinx 上怎么表现」是最便宜的真值：

1. 编带同一份记录代码的真值 Ryujinx：`bash compat/truth/build_truth.sh`。
2. 两边各跑一局，都设 `S2A_IPC_RECORD=<文件>`，按键节奏尽量一致。
3. 对拍，找第一处分歧：`python3 tools/ipc_diff.py <真值记录> <我方记录> --out 差异全表.tsv`。按（服务, 命令）对齐，分缺调用、多调用、返回码、出参、入参、句柄六类列出。

要注意两点：

- **Ryujinx 也有错。** 如果两边都一样失败（例如两边都一直扩堆），Ryujinx 就当不了这一项的真值。这时要回到 Switch 的系统语义，看真机上它应该回答什么。
- 拿到的读数不完整时（局被强杀、输出缓冲丢了），保留 Ryujinx 自己的日志文件再跑，不要用半截读数下结论。

### 3.4 卡在菜单 / 剧情 / 建档：自动玩家

- **先看图，不猜帧号。** 驾驶员每问一次都把截图存进局目录 `vision/v<序号>.png`、答案存 `vision/v<序号>.json(.log)`，卡住收局时另存 `ap_stuck.png`；`host.log` 里「自动玩家：」行写着每步按了什么、画面变没变。走过的页自动记进学路线 `~/.s2arm/run/s2arm/ap_learn/<程序号>.tsv`，下一局先回放。要录某一刻的画面给帧录放查，用 `S2A_AP_LIVE` 写 `REC:<名>`。
- **到了可操作场景就存档**，之后每局都从存档起（`tools/mac_save.sh`），不要每局都从开场重走建档菜单。

### 3.5 画面

- 判「画没画出来」要用彩色帧按 RGB 量。只看亮度时，暗红色会消失。
- 两局画面对比用 `tools/direct_compare`（逐块 SSIM、像素差、热图），只看全帧均值会漏掉局部错误。
- 宽高比、拉伸、居中要给测量读数，不报目测。拿 16:9 真值当尺子，不拿另一张宽屏图当尺子。
- 自动判读漏小目标（火苗、粒子）。最终观感由维护方在真机上连续看。

### 3.6 帧率 / 首遇 / 读回 / 分配（离线脚本，只读）

| 脚本 | 回答什么 |
|---|---|
| `python3 tools/game_fps.py <局目录>` | 游戏自己要的帧率（取交换间隔，不查表） |
| `python3 tools/frame_gate.py <局目录>` | 每帧分配有没有超闸门 |
| `python3 tools/firstuse_scan.py <局目录>` | 局里有几次着色器首遇现编、跳过绘制 |
| `python3 tools/readback_report.py <局目录>` | 谁让 CPU 等 GPU 读回，按耗时排行 |
| `python3 tools/score_cells.py <局目录> --game=<款> --commit=<提交> --diag=1` | 记分板五格的离线读数 |

**帧率、能耗、读回取舍只认真机读数。** Mac 会低估读回和同步的代价，第 5 节第 4 条有实例。真机 A/B 由维护方的列车排（`tools/ab.sh`）：底层性能改动缺省关合入，真机同包 A/B 达标后再翻缺省。

### 3.7 修完怎么验

- 单测要能反证：同一个单测在旧代码上红、新代码上绿。PR 里两个结果都写。
- 修复后用同一产物根跑**一局**确认越过原失败点，不要堆局数。触发条件已知的问题，新旧各注入一次就够了。
- 汇报用「期望 → 真结果」对位表；没验证的项照实写「没验证」，不要写成「已修好」。

## 4. 提交

- 提 PR 前跑一次 `bash tools/contrib_check.sh`，把摘要贴进 PR。它按改动文件挑步骤：只改文档不跑步骤，只改 `tools/ tests/ pack/` 只跑单测，其余全档。变基、拼提交在跑它之前做完，不要每改一行就跑一遍。
- 新 `.sh` 先过两项 lint：新出现的共享路径要在 `tools/shared_paths.tsv` 登记；脚本要能被 macOS 自带的 `/bin/bash 3.2` 解析。门禁会用 3.2 查全仓库 `.sh` 的语法。
- 跑自检时不要带着列车用的环境变量，例如 `env -u MERGE_OWNER bash tools/contrib_check.sh`，否则会误报环境红。
- 你本机缺维护方产物的那一项（例如本机共享根没有改写产物，导致 iOS 全量编译红）在摘要里写明，以维护方门禁为准。

## 5. 经验与教训（维护方踩过、改过机制的）

每条都对应过一次真实的返工。细节和更多条目见 [坑记录](坑记录.md)、性能与开发测试经验。

**测试方法**

1. **先写清这一局要证明什么。** 能用单测、读日志、离线重算回答的，就不起局。8 路 48 局的大批量曾被叫停：大部分局什么都没证明。
2. **A/B 只差一个变量。** 两局同时差模式、代码和产物根，曾把暗黑2 的 GPU 错误错归给宽屏，20 分钟后撤回。二分之前，先在「好」的那个提交上用同一量法确认它确实干净。
3. **报 A/B 之前核每帧绘制数是否同量级。** 塞尔达有一局 A 局停在 DLC 介绍页被判成 MARK，报出了一个假的 +2.49 W。
4. **Mac 读数不能放行读回 / 同步类改动。** 有一次 Mac 上 +0.5 ms 被放行，结果真机巫师3 读回 44 秒。
5. **改了线程睡眠、时钟或调度、又缺省开的改动，合入前至少真机冷启一款，看首帧时间。** 读时钟闸在 Mac 上没验到位就合了，暗黑3 真机冷启 60 秒 0 帧。
6. **一局干净不能排除偶发。** 巫师3 用一局对照就报「不是这个原因」，后来被推翻。要否定偶发，先看现场、找第一处分歧；或者用 `S2A_DIAG_DELAY` 把偶发变成稳定复现。
7. **停帧先看宿主线程栈。** 异度3 停帧时追了一天条件变量，最后线程栈一眼就看出来了。
8. **诊断开关先在 Mac 上核出数，再上真机。** 一个在 Metal 4 上从不出数的开关上了真机，白占一局。
9. **MARK 必须核截图。** 自动玩家曾 4 次把菜单误判成进了游戏。
10. **判据会「绿着失效」。** 报绿时同时报扫了多少、分母多少。列表截断后没出现的项不等于 0。
11. **重跑变绿可能是假象。** 同一棵树里增量 make 会跳过上次失败的目标，真失败就被放过了。重跑要从干净状态开始。

**工具与环境**

12. **管道会吞退出码。** `cmd | tail -1 && next` 在 cmd 失败时照样往下走。先存 rc，或用 `set -o pipefail`。
13. **脚本改代码要断言替换命中。** 替换没命中、没报错的提交出过两次。
14. **跑长脚本时别原地改它。** bash 是边跑边按偏移读的，要改就先拷一份冻结副本来跑。
15. **几局并行时局目录要私有。** 共享的 `~/Documents`、着色器缓存或宏语料目录会让并行局互踩。`run_mac.sh` 缺省已经把它们指到局目录，自己写的脚本别指回共享位置。
16. **删克隆不回空间。** APFS 上 du 看着几百 GB 的旧产物，删了 df 可能几乎不涨。清盘按 df 前后量。
17. **静态链接会丢只靠段登记的 `.o`。** 一个只靠自定义段登记的对象被链接器丢掉，运行时调到空指针。单测要按宿主同样的方式静态链接。
18. **进 App 的代码要用 iOS SDK 编一遍。** Mac 宿主编得过不代表 iOS 编得过，例如 `mach_vm.h` 的差异就弄坏过一次 iOS 出包。

**判断与汇报**

19. **报告里写明「未验证」的现象，不当缺陷去修。** 有一次按一份写明「手柄状态未验」的报告改了重连策略、回了「已修好」，作者更正后整笔撤回。
20. **解包失败、源文件坏、游戏不支持，三者分开记。** 解不开先怀疑我方工具；源文件坏要换一份完整原件确认；只有 32 位程序记「不支持」。
21. **找根因，不按款打补丁。** 修复落在共用层，并对照 Switch 的语义（Ryujinx 是首选参照，但它也会错）。按某一款写的特判，下一款还会再踩。
